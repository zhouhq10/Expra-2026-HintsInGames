## Before the meeting

**Context from last week:**

We discussed several candidate task families and some first pros/cons:

- **Sudoku / IQ-test style tasks** - interesting, but may be hard to standardize and may bring large individual differences.
- **Lights Out** - easy to track progress, but hard to write hints that are more than disguised solutions.
- **Constraint-satisfaction / Mastermind / ARC / constrained crossword** - likely easier to write distinct hints for.
- **Tower of Hanoi** - simple and well-studied, need more planning.
- **Maze with keys/doors/limited visibility** - easy to track progress, but we need enough structure to make it non-trivial to generalize across tasks.

We also discussed that:

- We should start from **general hints** rather than customized hints.
- Hints should appear **when the player is stuck**.
- The chosen game should contain a **general failure case / bottleneck**, for example a clearly more difficult puzzle in the middle of play, so that hint timing and usefulness can be tested.
- If this works in the prototype, we can later consider scaling from general hints to **more customized hints**.

## This week's task

This week, you should organize **one group meeting without me** and use it to turn last week's discussion into a **rough but concrete design**.

- the **chosen game**

### 1. Finalize the game choice

Choose **one game** as the direction for the prototype.

Write:

- the chosen game
- one short reason why this is the best option now
- one main risk or weakness that still needs attention
- one backup option, if you think it is necessary

### 2. Produce a rough game design

For the chosen game, write a concrete rough design.

Please include:

- what the player does
- what the goal is
- what one puzzle/trial looks like
- how the task is split into a **training phase** and a **test phase**
- how many puzzles/trials you roughly imagine for the **training phase**
- how many puzzles/trials you roughly imagine for the **test phase**
- whether there should be levels, stages, or increasing difficulty
- where the likely **failure case / bottleneck** is
- how the **training games** and **test games** share the same underlying structure
- how the test phase checks whether learning transfers **without hints**
- how player progress can be logged


### 3. Produce a rough hint design

For the chosen game, write a first rough design of the hint system.

Please use the three hint conditions from our project:

- **Direct hint** - tells the player what to do
- **Strategy hint** - explains the relevant principle
- **Reflective hint** - prompts the player to think without giving the answer

Please include:

- what a **general hint** means in your chosen game
- what type of game state or failure case the hint responds to
- why the same overall hint logic can be reused across several training puzzles
- why the three hint conditions can be kept clearly different from each other

Then, for **one specific example puzzle state**, write:

- one **Direct hint**
- one **Strategy hint**
- one **Reflective hint**

These three hints should all address the **same underlying problem**, but differ in how much they tell the player.

Then answer these design questions:

- In this game, what does a **Direct hint** sound like without becoming a full solution?
- In this game, what does a **Strategy hint** teach that could help on later puzzles?
- In this game, what does a **Reflective hint** ask or highlight so that it still feels like help rather than no help?
- Is the chosen game good for comparing these three hint types, or do the three hints collapse into nearly the same thing?

The point is to make sure the game supports a meaningful comparison between:

- immediate help on the current puzzle
- learning something useful for later puzzles
- preserving the player's sense of agency

If useful, you can also note whether the game seems compatible with later **customized hints**, but that is not the priority this week.

### 4. Design the bottleneck / difficult point

Our current direction is that hints should appear **when the player is stuck**, so the game sequence should contain a **clear bottleneck / difficult point** where this becomes meaningful.

For your chosen game, write:

- where in the sequence the bottleneck should appear
- what makes this point more difficult than the surrounding puzzles
- what kind of mistake, confusion, or failure case you expect players to have there
- why this bottleneck is useful for testing hints
- whether the same bottleneck structure can be reused across multiple training puzzles

Please connect this to both the game design and the hint design.  
The point is to design a game sequence where the need for help is not random, but tied to a meaningful challenge in the task.
